1 Требования к продукту
1.1 Назначение продукта
Система предназначена для хранения истории погодных наблюдений по выбранным городам, построения краткосрочного прогноза температуры воздуха и количественной оценки точности используемой модели.
Оценка точности вынесена в назначение наравне с прогнозированием. Система не только предсказывает значение температуры, но и измеряет качество собственных прогнозов, сопоставляя их с фактическими наблюдениями и сравнивая с тривиальным бейзлайном.
1.2 Пользователи системы
Выделены две роли пользователей.
Наблюдатель просматривает историю наблюдений по выбранному городу и текущий прогноз температуры. Его интересует фактическая динамика показателей и ожидаемые значения.
Аналитик модели оценивает качество прогнозов: метрики точности, сравнение с бейзлайном, разрезы по горизонту прогноза и по городам. Его интересует, работает ли модель и до какого горизонта прогнозирования она сохраняет практический смысл.
Вторая роль является законной для исследовательского проекта: специалист, оценивающий качество модели, выступает таким же пользователем системы, как и наблюдатель. Под эту роль предусмотрен отдельный экран с метриками.
1.3 Основной сценарий работы
1)	Пользователь открывает систему и выбирает город из списка доступных.
2)	Система отображает историю наблюдений за выбранный период.
3)	Пользователь запрашивает прогноз температуры.
4)	Система строит прогноз на каждый час в диапазоне до 48 часов вперёд и сохраняет каждое значение в базу данных с указанием момента построения, целевого момента, горизонта и модели.
5)	Пользователь видит прогноз на графике как продолжение истории наблюдений.
6)	При наступлении прогнозируемого момента и поступлении фактического наблюдения система сопоставляет прогноз с фактом и рассчитывает ошибку.
7)	Пользователь видит накопленные метрики точности в сравнении с бейзлайном.
Шестой шаг выполняется асинхронно по отношению к остальным: прогноз, построенный в текущий момент, становится доступным для оценки только по истечении соответствующего горизонта.
1.4 Функциональные требования
Требования сформулированы в проверяемом виде, допускающем однозначную оценку выполнения.
Работа с данными:
- ФТ-1. Система загружает исторические погодные наблюдения из внешнего источника по заданному городу и периоду.
- ФТ-2. Система сохраняет наблюдения в базу данных: температура, влажность, приземное давление, давление, приведённое к уровню моря, осадки, с часовым шагом.
- ФТ-3. Система не допускает дублирования наблюдений: пара «город и момент наблюдения» уникальна, повторная загрузка того же периода обновляет существующую запись.
- ФТ-4. Список городов фиксируется при инициализации системы и не изменяется через пользовательский интерфейс.
Просмотр данных:
- ФТ-5. Пользователь может выбрать город из списка доступных.
- ФТ-6. Пользователь может просмотреть историю наблюдений за выбранный период.
- ФТ-7. Система отображает историю наблюдений в виде графика.
Прогнозирование:
- ФТ-8. Пользователь может запросить прогноз температуры для выбранного города.
- ФТ-9. Система рассчитывает прогноз на каждый час в диапазоне от 1 до 48 часов вперёд.
- ФТ-10. Система рассчитывает прогноз по бейзлайну для тех же моментов и горизонтов.
- ФТ-11. Система сохраняет каждое прогнозное значение с указанием города, момента построения, целевого момента, горизонта и модели.
- ФТ-12. Система отображает прогноз на графике как продолжение фактических наблюдений.
Оценка точности:
- ФТ-13. Система сопоставляет ранее построенные прогнозы с фактическими наблюдениями по городу и целевому моменту.
- ФТ-14. Система рассчитывает MAE и RMSE отдельно для каждой модели, включая бейзлайн.
- ФТ-15. Система рассчитывает отношение MAE модели к MAE бейзлайна.
- ФТ-16. Система отображает метрики точности в разрезе города и горизонта прогноза.
- ФТ-17. Система отображает зависимость средней ошибки от горизонта прогноза.
1.5 Границы проекта
В состав минимально жизнеспособного продукта входят: загрузка и хранение наблюдений по двум городам, сезонный наивный бейзлайн с лагом 24 часа, линейная регрессия на лаговых признаках, сохранение каждого прогноза с полным контекстом, аналитика средствами SQL с использованием оконных функций, расчёт MAE и RMSE с отношением к бейзлайну, интерфейс с выбором города, графиком и таблицей метрик.
За границы текущего MVP сознательно вынесены: прогнозирование влажности, давления и осадков, которые только хранятся и анализируются; добавление и удаление городов через интерфейс; авторизация, регистрация и роли пользователей; сложная визуализация и кастомизация дашборда; автоматический выбор лучшей модели и переобучение по расписанию; обновление данных в реальном времени; микросервисная архитектура и распределённые вычисления.
2 Данные и метрики
2.1 Входные данные
Из внешнего источника Open-Meteo по каждому городу поступает временной ряд с часовым шагом. Состав полей приведён в таблице 1.
Таблица 1 - Состав входных данных
Поле	Единица	Назначение
Метка времени	ISO 8601	Момент наблюдения
Температура	°C	Целевая переменная прогноза
Относительная влажность	%	Хранение и аналитика
Приземное давление	гПа	Хранение и аналитика
Давление к уровню моря	гПа	Сопоставимость городов между собой

Используются два эндпоинта источника: Historical Weather API для формирования обучающей выборки глубиной не менее трёх лет и Forecast API с параметром past_days для получения актуальных фактических наблюдений. Второй необходим потому, что архив публикуется с задержкой около одних суток, а для сопоставления с ранее построенными прогнозами требуются свежие данные.
Справочные сведения о городах задаются при инициализации системы: название, географические координаты, часовой пояс, высота над уровнем моря.
2.2 Результаты работы вычислительного модуля
Вычислительный модуль порождает прогнозные значения температуры. Каждое значение сохраняется вместе с контекстом: идентификатор города, момент построения прогноза, целевой момент времени, горизонт прогнозирования и использованная модель.
Один запуск расчёта порождает 48 записей на каждую пару «город и модель», по одной на каждый час горизонта. Для каждого горизонта обучается отдельная регрессионная модель, поскольку целевая переменная у них различна.
2.3 Состав сохраняемых данных
В базе данных сохраняются справочник городов, наблюдения, конфигурации моделей и построенные прогнозы.
Ошибки прогнозов не сохраняются. Они вычисляются соединением таблиц прогнозов и наблюдений в момент выполнения запроса. Хранение производных величин создавало бы риск рассинхронизации при переобучении модели или уточнении исходных данных. При недостаточной производительности запросов предполагается введение материализованного представления, что относится к этапу оптимизации, а не к модели данных.
2.4 Метрики качества модели
Метрики рассчитываются по соединению прогнозов с наблюдениями по паре «город и целевой момент времени». Состав метрик приведён в таблице 2.
Таблица 2 - Метрики качества прогнозирования
Метрика	Содержание	Источник данных
MAE	Средняя абсолютная ошибка прогноза в градусах	Прогнозное значение, фактическая температура
RMSE	Среднеквадратичная ошибка, усиленно штрафует крупные промахи	Прогнозное значение, фактическая температура
Отношение MAE	Отношение ошибки модели к ошибке бейзлайна; значение менее единицы означает выигрыш	Рассчитанные значения MAE обеих моделей
MAE и RMSE рассчитываются отдельно для каждой модели, включая бейзлайн. Основным показателем принято отношение ошибок: абсолютное значение ошибки само по себе не позволяет судить о качестве модели.
2.5 Аналитические разрезы
Каждый разрез реализуется группировкой по существующему полю и не требует дополнительных данных.
- По горизонту прогноза. Ожидается монотонный рост ошибки с увеличением горизонта; нарушение монотонности указывает на дефект реализации. Позволяет построить кривую деградации точности, отвечающую на вопрос о предельном горизонте применимости модели.
- По городу. Сопоставление Алматы и Астаны. Резко континентальный климат Астаны предполагает более высокую изменчивость показателей и, вероятно, большую ошибку прогноза.
- По времени суток. Извлекается из целевого момента времени. Предполагается, что наибольшая ошибка приходится на переходные часы.
- По месяцу. Устойчивость погодных условий различается по сезонам года.
2.6 Метрики накопления данных
Характеризуют состояние системы, а не качество модели.
- Количество наблюдений в разрезе городов.
- Количество построенных прогнозов в разрезе моделей и горизонтов.
- Глубина покрытия данными и наличие пропусков в ряду.
- Доля прогнозов, для которых уже получено фактическое наблюдение. Отражает механику работы системы: прогноз, построенный в текущий момент, становится оцениваемым только по истечении горизонта.
2.7 Аналитика временного ряда
Реализуется оконными функциями SQL в соответствии с требованиями темы проекта.
- Скользящее среднее температуры за заданное окно.
- Минимальное и максимальное значение за период в разрезе города.
- Суточная амплитуда температуры как разность максимума и минимума внутри суток.
- Сравнение городов по средним значениям за месяц.
- Формирование лаговых признаков функциями смещения.
Все перечисленные метрики вычисляются из полей, определённых в модели данных. Введения дополнительных сущностей и атрибутов не требуется.
3 Концептуальная модель данных
Модель включает четыре сущности. Типы данных, первичные и внешние ключи на данном этапе не определяются и относятся к физическому уровню проектирования.
3.1 Сущности и атрибуты
Таблица 3 - Сущности концептуальной модели
Сущность	Атрибуты
Город	Название, широта, долгота, часовой пояс, высота над уровнем моря
Наблюдение	Момент наблюдения, температура, влажность, приземное давление, давление к уровню моря, осадки
Модель	Название, версия, параметры обучения, дата обучения
Прогноз	Момент построения, целевой момент, горизонт, прогнозное значение температуры
Атрибут «высота над уровнем моря» необходим, поскольку приземное давление зависит от высоты точки наблюдения. Астана расположена на высоте около 350 метров, Алматы около 800 метров, вследствие чего приземное давление у них различается на десятки гектопаскалей независимо от погодных условий. По этой же причине давление хранится двумя атрибутами: приземное в измеренном виде и приведённое к уровню моря для сопоставимости городов.
Параметры обучения модели хранятся единым атрибутом, поскольку наборы параметров различных моделей не пересекаются: у сезонного наивного прогноза это период сезонности, у линейной регрессии перечень лагов и глубина обучающей выборки, у модели Хольта-Уинтерса три коэффициента сглаживания. Размещение их в отдельных колонках привело бы к разреженной таблице и потребовало бы изменения схемы при каждом новом эксперименте.
Сущность «Прогноз» содержит два различных момента времени: момент построения прогноза и целевой момент, на который прогноз сделан. Сопоставление с фактическим наблюдением выполняется по целевому моменту, момент построения подтверждает, что прогноз получен заблаговременно.
3.2 Связи и кардинальности
Таблица 4 - Связи между сущностями
Связь	Кардинальность	Содержание
Город - Наблюдение	1 : N	В одном городе регистрируется множество наблюдений; каждое наблюдение относится ровно к одному городу

3.3 Связь прогноза с фактическим наблюдением
Прямая связь между сущностями «Прогноз» и «Наблюдение» в модели отсутствует, что является осознанным проектным решением.
В момент создания прогноза соответствующее наблюдение ещё не существует: прогноз строится заблаговременно, фактическое значение поступает по истечении горизонта. Внешний ключ при этом указывал бы на несуществующую запись. Более того, сама возможность установить такую ссылку означала бы, что прогноз построен задним числом, что система должна исключать.
Связь существует на логическом уровне и реализуется соединением по составному условию равенства города и равенства целевого момента прогноза моменту наблюдения. Данная пара полей является центральной связью системы, на которой основан аналитический модуль.
3.4 Ограничения целостности
Пара «город и момент наблюдения» уникальна. Повторная загрузка того же периода обновляет существующую запись, не создавая дубликата. На концептуальном уровне ограничение фиксируется как бизнес-правило, механизм реализации определяется на этапе физического проектирования.
3.5 Отклонение от третьей нормальной формы
Атрибут «горизонт» сущности «Прогноз» функционально выводится из разности целевого момента и момента построения, то есть формально является избыточным.
Решение о его хранении принято сознательно по двум причинам. Во-первых, горизонт представляет собой параметр пользовательского запроса, а целевой момент является производным от него результатом, то есть концептуально это входная, а не вычисляемая величина. Во-вторых, расчёт прогнозов выполняется не строго в начале часа, вследствие чего вычисленная разность принимала бы дробные значения, что разрушило бы группировку по горизонту в аналитическом модуле.
4 Предварительная архитектура системы
Архитектура построена по слоистому принципу. Микросервисное разделение не применяется: для минимально жизнеспособного продукта с двумя городами распределённая архитектура избыточна.
 
Рисунок 2 - Схема предварительной архитектуры
4.1 Состав компонентов
Интерфейс представляет собой одну веб-страницу, обеспечивающую выбор города, отображение графика наблюдений с продолжением в виде прогноза и таблицы метрик точности. Взаимодействие с сервером осуществляется исключительно по протоколу HTTP, собственная вычислительная логика отсутствует.
Серверная часть реализуется средствами FastAPI и предоставляет REST API. Принимает запросы интерфейса, вызывает соответствующий модуль и возвращает результат в формате JSON. Выбор технологии обусловлен требованиями дисциплины к проектированию API-контрактов, а также автоматической генерацией документации.
Вычислительный модуль обеспечивает обучение моделей и построение прогнозов. Для каждого горизонта от 1 до 48 часов обучается отдельная регрессионная модель. Здесь же рассчитываются значения бейзлайна.
Аналитический модуль выполняет запросы к базе данных с использованием оконных функций: соединение прогнозов с фактическими наблюдениями, расчёт метрик, скользящие агрегаты, формирование разрезов. Реализация средствами SQL, а не вычислениями на стороне приложения, является требованием темы проекта.
Загрузчик обращается к внешнему источнику, приводит полученный ответ к табличному виду и сохраняет данные в базу, обеспечивая защиту от дублирования при повторном запуске.
Внешним источником выступает сервис Open-Meteo, используемый через два эндпоинта, описанных в подразделе 2.1.
4.2 Потоки взаимодействия
Интерфейс обращается исключительно к серверной части. Серверная часть управляет тремя модулями, не выполняя вычислений самостоятельно. Все модули взаимодействуют с базой данных: вычислительный читает наблюдения и записывает прогнозы, аналитический выполняет только чтение, загрузчик только запись.
Прямой обмен данными между модулями отсутствует: их связывает база данных. Такое решение упрощает отладку, поскольку состояние системы в любой момент времени доступно для просмотра в таблицах.
4.3 Предварительный характер решения
Приведённая схема отражает логическое разделение ответственности между компонентами, а не физическое развёртывание. На этапе Спринта 3 после проверки Proof of Concept будет уточнено, выполняются ли модули как отдельные процессы, применяется ли синхронный вызов и требуется ли фоновая задача для периодического пересчёта прогнозов.
Остаётся открытым вопрос оформления загрузчика: как сервиса либо как отдельно запускаемого скрипта. Для минимально жизнеспособного продукта достаточно скрипта, однако при введении автоматического пересчёта по расписанию потребуется планировщик задач.
5 Минимально жизнеспособный продукт
5.1 Минимальный сквозной сценарий
Версия продукта признаётся минимально жизнеспособной при работоспособности следующей цепочки без ручного вмешательства.
1)	Загрузчик получает историю наблюдений по Алматы и Астане из внешнего источника и сохраняет её в базу данных.
2)	Вычислительный модуль обучается на полученных данных и строит прогноз температуры на каждый час до 48 часов вперёд.
3)	Каждое прогнозное значение сохраняется в базу с указанием города, момента построения, целевого момента, горизонта и модели.
4)	Аналогичным образом формируется прогноз по бейзлайну.
5)	Аналитический модуль соединяет ранее построенные прогнозы с фактическими наблюдениями и рассчитывает MAE и RMSE для обеих моделей.
6)	Пользователь открывает страницу, выбирает город и получает график истории с продолжением в виде прогноза, а также таблицу метрик с отношением ошибки модели к ошибке бейзлайна.
При неработоспособности любого звена цепочки минимально жизнеспособный продукт считается несостоявшимся. Данный сценарий не подлежит сокращению ни при каких обстоятельствах.

6 План разработки
Управление задачами ведётся на доске GitHub Projects, связанной с репозиторием проекта. Доска содержит колонки Backlog, To Do, In Progress, Review и Done. Для каждой задачи определены принадлежность к спринту, исполнитель и текущий статус.
Проект выполняется индивидуально, исполнителем всех задач является автор. Ограничение незавершённой работы установлено на уровне двух задач одновременно.
6.1 Спринт 3, недели 5-6. Проектирование
- Спроектировать физическую схему базы данных с приведением к третьей нормальной форме.
- Определить состав индексов и обосновать каждый из них.
- Подготовить DDL-скрипты создания схемы.
- Реализовать ограничение уникальности наблюдений.
- Описать API-контракты: эндпоинты, методы, параметры, форматы ответов, статус-коды.
- Выполнить Proof of Concept загрузки данных в реальную базу.
- Пройти Architecture Review и зафиксировать замечания.
6.2 Спринт 4, недели 7-8. Вычислительное ядро
- Загрузить полную историю наблюдений по двум городам.
- Проверить однородность ряда на границе источников реанализа.
- Реализовать формирование лаговых и циклических признаков.

- Реализовать обучение регрессионных моделей по горизонтам.
